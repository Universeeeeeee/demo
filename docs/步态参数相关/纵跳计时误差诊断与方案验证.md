# 纵跳计时误差诊断与方案验证

> 2026-06-24 更新：本文保留 session5 的历史诊断结果。文中的“边界记录 + 事件确认”不能再理解为简单寻找最早小簇或 touch/lift 统一 onset 回填；当前实施准则是“同一份 `raw_clusters` 派生确认簇，并用时空关联 raw track 回填统计边界”。若本文早期描述与当前准则冲突，以本更新和 `plan.md` 为准。

## 1. 背景

本次主要排查纵跳模式下触地时间、腾空时间和人工视频标注差距较大的问题。

一开始怀疑是 `confirm_samples=2` 带来的确认延迟，但进一步分析后发现，这个延迟在触地和离地两端可能会相互抵消，不一定是主要误差来源。更值得关注的是事件边界本身：当前触地要等主接触簇比例达到较高阈值后才确认，离地则依赖低阈值或有效主簇消失，这两类边界偏移不一定对称，所以会直接影响触地时间和腾空时间。

本次没有直接修改主检测逻辑、统计逻辑、界面或报告模块，而是先用离线脚本复盘单次实验数据，验证不同事件时间口径到底会带来多大变化。

## 2. 数据来源

- 数据库会话：`test_sessions.id = 5`
- 会话开始时间：`2026-06-03 14:24:54`
- 逐帧数据：`data/led_frames_20260603_142723.xlsx`
- 人工标准：视频手动标注的 5 次触地时间和腾空时间
- 诊断输出：`docs/步态参数相关/timing_diagnostics/session5/summary.md`

虽然数据库会话时间和 Excel 文件名时间不完全一致，但离线复盘结果和会话指标能够对上，因此本次默认这份逐帧数据可用于分析。

## 3. 已完成的历史验证方案

session5 对同一份逐帧数据跑了三种口径。这一版诊断中的第三种方案是早期近似，用于判断“发现边界”和“确认事件”是否值得拆开，不等同于最终生产方案。

| 方案 | 做法 | 目的 |
|---|---|---|
| 当前算法 | 连续 2 帧确认后，使用确认成功帧时间作为事件时间 | 作为基线，复现当前程序行为 |
| 确认帧补偿 | 判定逻辑不变，只把事件时间回填到第一次满足确认条件的帧 | 验证“确认延迟”是否是主要误差来源 |
| 早期边界记录 + 事件确认 | 用较低门槛记录 onset，再用高阈值确认事件有效 | 探索“边界时间”和“事件可靠性”拆开后是否更准 |

其中，当前算法和确认帧补偿都保留原有状态机，包括：

- 有效主簇长度过滤；
- 触地、离地阈值；
- 连续帧确认；
- streak 递减规则；
- 事件触发后的状态切换。

早期边界记录 + 事件确认方案额外区分两套接触簇：

- 小簇用于记录可能的触地或离地 onset；
- 原有效主簇仍用于确认事件，避免小噪声直接变成有效事件。

后续正式验证不再采用这个简化定义，而应改为：

- 每帧只提取一次 `raw_clusters`；
- `confirm_cluster` 从 `raw_clusters` 中按当前生产规则筛出；
- touch 用关联 raw track 的 `first_seen_time`；
- lift 第一阶段不改当前确认语义，只在当前确认成立时回填同一 active track 的 `last_seen_time`；
- 是否升级 lift 确认规则，另立实验版本验证，不能混入本阶段。

## 4. 对比结果

本次优先采用和 `GaitEngine` 当前统计规则一致的配对口径，而不是简单的 `touch_i -> lift_i -> touch_{i+1}` 三元组。原因是首个三元组可能包含起跳前站立或准备阶段，直接拿来和人工第 1 次跳跃配对会放大误差。

| 方案 | 触地平均绝对误差 | 腾空平均绝对误差 | 误差方向 | 判断 |
|---|---:|---:|---|---|
| 当前算法 | 57.8ms | 41.7ms | 触地偏短，腾空偏长 | 当前基线 |
| 确认帧补偿 | 57.8ms | 41.7ms | 触地偏短，腾空偏长 | 基本没有改善 |
| 早期边界记录 + 事件确认 | 38.3ms | 22.1ms | 仍有偏差，但明显缩小 | 支持继续验证边界回填方向 |

结果说明：单纯把连续 2 帧确认带来的时间往前补，并不能明显改善误差；更值得继续验证的是把“发现边界”和“确认事件”拆开处理。但 session5 只有一组数据，且第三种方案只是早期 onset 近似，不能直接作为生产改造依据。

## 5. 结论

当前这组数据下，算法结果相对人工标注表现为：

- 触地时间偏短；
- 腾空时间偏长；
- 确认帧补偿几乎没有收益；
- 边界记录 + 事件确认明显更接近人工标注。

因此，不建议简单降低触地阈值，也不建议现在就大改统计层。更合理的方向是：在检测层维护可解释的原始接触轨迹，同时继续保留当前高阈值和连续帧确认来保证事件可靠性。回填时不能简单取窗口内最早非零帧，而要证明候选小簇和确认簇在时间、空间上属于同一次接触演化。

如果后续多组数据都能复现这个趋势，可以考虑调整 `FootEvent` 语义：

```python
@dataclass
class FootEvent:
    kind: str
    time: float              # 用于统计的边界时间
    ratio: float
    centroid_cm: Optional[float]
    confirm_time: Optional[float] = None  # 确认成功帧时间，仅用于调试
    first_confirm_frame_time: Optional[float] = None  # 首个满足当前确认条件的帧
```

这样 `GaitEngine._accumulate_hop_stats()` 仍然继续使用 `ev.time`，统计层不需要大改。

## 6. 后续安排

1. 先更新离线诊断脚本，新增关联 raw track，而不是立即改生产链路。
2. 至少比较 A 当前确认帧、B 首个确认条件帧、C touch-only 关联 `first_seen`、D lift-only 当前确认语义下关联 `last_seen`、E touch+lift 关联回填。
3. 记录 `candidate_to_confirm_ms`、候选簇长度、候选簇位置、确认簇位置、匹配分数、fallback 原因，用于判断阈值是否合理。
4. 对 `max_missing_frames`、`max_edge_gap_led`、`max_centroid_shift_led`、`max_touch_candidate_age_ms` 做小范围敏感性比较。
5. 至少 3 个独立 session、15~20 个完整跳跃通过验证后，再小范围修改 `SingleFootDetector` 主逻辑。
6. 第一阶段 lift 只做当前确认语义下的 `last_seen_time` 回填，不桥接确认后才出现的小簇；若要升级 lift 确认规则，作为单独算法版本验证。
7. 修改主逻辑前，不改界面、不改报告、不改统计层，先保证事件时间语义稳定。
