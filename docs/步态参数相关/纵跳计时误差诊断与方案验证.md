# 纵跳计时误差诊断与方案验证

## 1. 背景

本次主要排查纵跳模式下触地时间、腾空时间和人工视频标注差距较大的问题。

一开始怀疑是 `confirm_samples=2` 带来的确认延迟，但进一步分析后发现，这个延迟在触地和离地两端可能会相互抵消，不一定是主要误差来源。更值得关注的是事件边界本身：当前触地要等主接触簇比例达到较高阈值后才确认，离地则依赖低阈值或有效主簇消失，这两类边界偏移不一定对称，所以会直接影响触地时间和腾空时间。

本次没有直接修改主检测逻辑、统计逻辑、界面或报告模块，而是先用离线脚本复盘单次实验数据，验证不同事件时间口径到底会带来多大变化。

## 2. 数据来源

- 数据库会话：`test_sessions.id = 5`
- 会话开始时间：`2026-06-03 14:24:54`
- 逐帧数据：`data/led_frames_20260603_142723.xlsx`
- 人工标准：视频手动标注的 5 次触地时间和腾空时间
- 诊断输出：`docs/步态参数相关/timing_diagnostics/session5/summary.md`

虽然数据库会话时间和 Excel 文件名时间不完全一致，但离线复盘结果和会话指标能够对上，因此本次默认这份逐帧数据可用于分析。

## 3. 验证方案

本次对同一份逐帧数据同时跑了三种口径：

| 方案 | 做法 | 目的 |
|---|---|---|
| 当前算法 | 连续 2 帧确认后，使用确认成功帧时间作为事件时间 | 作为基线，复现当前程序行为 |
| 确认帧补偿 | 判定逻辑不变，只把事件时间回填到第一次满足确认条件的帧 | 验证“确认延迟”是否是主要误差来源 |
| 边界记录 + 事件确认 | 先用小接触簇记录可能的边界时间，再用高阈值确认事件有效 | 验证“边界时间”和“事件可靠性”拆开后是否更准 |

其中，当前算法和确认帧补偿都保留原有状态机，包括：

- 有效主簇长度过滤；
- 触地、离地阈值；
- 连续帧确认；
- streak 递减规则；
- 事件触发后的状态切换。

边界记录 + 事件确认方案额外区分两套接触簇：

- 小簇用于记录可能的触地或离地边界；
- 原有效主簇仍用于确认事件，避免小噪声直接变成有效事件。

## 4. 对比结果

本次优先采用和 `GaitEngine` 当前统计规则一致的配对口径，而不是简单的 `touch_i -> lift_i -> touch_{i+1}` 三元组。原因是首个三元组可能包含起跳前站立或准备阶段，直接拿来和人工第 1 次跳跃配对会放大误差。

| 方案 | 触地平均绝对误差 | 腾空平均绝对误差 | 误差方向 | 判断 |
|---|---:|---:|---|---|
| 当前算法 | 57.8ms | 41.7ms | 触地偏短，腾空偏长 | 当前基线 |
| 确认帧补偿 | 57.8ms | 41.7ms | 触地偏短，腾空偏长 | 基本没有改善 |
| 边界记录 + 事件确认 | 38.3ms | 22.1ms | 仍有偏差，但明显缩小 | 当前最优方向 |

结果说明：单纯把连续 2 帧确认带来的时间往前补，并不能明显改善误差；真正有效的是把“发现边界”和“确认事件”拆开处理。

## 5. 结论

当前这组数据下，算法结果相对人工标注表现为：

- 触地时间偏短；
- 腾空时间偏长；
- 确认帧补偿几乎没有收益；
- 边界记录 + 事件确认明显更接近人工标注。

因此，不建议简单降低触地阈值，也不建议现在就大改统计层。更合理的方向是：在检测层记录更早的候选边界时间，同时继续保留高阈值和连续帧确认来保证事件可靠性。这样既能减少时间误差，也不会把小噪声直接当成触地或离地事件。

如果后续多组数据都能复现这个趋势，可以考虑调整 `FootEvent` 语义：

```python
@dataclass
class FootEvent:
    kind: str
    time: float              # 用于统计的边界时间
    ratio: float
    centroid_cm: Optional[float]
    confirm_time: Optional[float] = None  # 确认成功帧时间，仅用于调试
```

这样 `GaitEngine._accumulate_hop_stats()` 仍然继续使用 `ev.time`，统计层不需要大改。

## 6. 后续安排

1. 再补几组带人工视频标注的纵跳数据，验证该结论是否稳定。
2. 保留离线诊断脚本，继续输出逐帧信息和事件对比表。
3. 重点观察不同确认窗口下的误差变化，避免候选边界记录得过早。
4. 如果多组数据都显示边界记录 + 事件确认更优，再小范围修改 `SingleFootDetector` 主逻辑。
5. 修改主逻辑前，不改界面、不改报告、不改统计层，先保证事件时间语义稳定。
