# 跑步机模式 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 Iron_Jump 中新增跑步机步态和跑步两类测试模式，使其拥有独立配置、独立算法处理、独立结果报告，并保留未来继续扩展更多模式的架构入口。

**Architecture:** 保留 `SessionController` 作为会话生命周期编排层，把当前偏纵跳/普通步态的 `GaitEngine` 收敛成模式运行时 facade，再把纵跳、跑步机步态、跑步机跑步拆到各自 processor/report/config 文件中。第一阶段采用“新增并列模块 + 旧入口兼容”的方式，避免一次性重命名造成 UI、agent、数据库、测试大面积震荡。

**Tech Stack:** Python dataclasses、qtpy/PySide6 Signal、SQLite、JSON config/report snapshot、pytest。

## 1. 当前事实

### 1.1 现有代码边界

当前代码中已经有几条可复用边界：

| 模块 | 当前职责 | 跑步机模式中的建议 |
| --- | --- | --- |
| `ui/session_controller.py` | 负责 prepare/start/stop，结束时构造 `TestReport`。 | 保留为公共会话控制器，不按模式复制。 |
| `engine/gait_engine.py` | 接收原始光栅帧，分发到纵跳或普通步态逻辑。 | 改成模式运行时 facade，实际算法下放给 processor。 |
| `config/test_report.py` | 生成不可变报告快照，已有 `JumpTestReport` 和 `GaitTestReport`。 | 新增跑步机 report 文件；旧 `build_report()` 仅保留为委托 `engine.build_report()` 的兼容 wrapper。 |
| `config/test_config.py` | 目前注释和字段偏 Jump Test，但 `mode_label` 已包含跑步机。 | 作为兼容入口保留；新增 `AnyTestConfig` 和并列 config 文件。 |
| `data/subject_store.py` | `test_sessions` 已保存 `config_json` 和 `report_summary_json`。 | 适合先用 JSON 快照保存多模式详情，再按查询需求拆表。 |
| `agent/llm_agent.py` / `agent/models.py` | prompt 和 `LLMTestConfig` 目前只支持 Jump Test。 | 后续按模式拆 prompt 和 Pydantic model。 |
| `ui/param_panel.py` | 从 `Iron_parameters.json` 读 schema，但部分分组仍是硬编码。 | 改为按 mode schema 渲染配置参数。 |

### 1.2 当前风险点

1. `GaitEngine.__init__()` 目前使用 `self._mode = "纵跳" if test_type == "Jump Test" else "步态分析"`。这意味着 `Treadmill Running Test` 和 `Treadmill Gait Test` 会被当成普通步态处理。
2. `TestConfig` 当前文件注释明确说“仅包含 Jump Test 相关字段”，不适合作为跑步机配置继续硬塞字段。
3. `TestReport` 只有 `JumpTestReport` 和 `GaitTestReport`，跑步机结果需要 Run Data、Gait Data、逐步有效性和汇总统计层。
4. `Iron_parameters.json` 需要保持 gait 使用 `min_step_length` / `Minimum step length`，running 使用 `min_gap_between_feet` / `Minimum gap between feet`；后续 schema 测试要防止这两个字段再次混用。
5. 文档中“参数”一词有混用：有时指 TestConfig，有时指 ResultMetric，有时指统计摘要。跑步机实现前必须统一口径。

### 1.3 说明书中的 Direction 口径

说明书第 4.2.2.5 Treadmill Running Test 和第 4.2.2.6 Treadmill Gait Test 对 `Direction` 的定义相同：它表示受试者 walking direction 是 `Interface side` 还是 `Opposite side`，也就是跑步/行走方向相对接口鼓的位置。

说明书给出的选择规则是：接口鼓在跑步机末端时选 `Opposite side`；反之选 `Interface side`。因此开发中不要把它理解成普通地面步态的进入方向、设备左右方向，或泛化的“行进方向”。本文统一使用内部字段 `direction`，UI 标签可以继续显示说明书的 `Direction`。

## 2. 术语边界

后续代码、文档、UI 文案统一使用以下四类词：

| 术语 | 英文建议 | 含义 | 示例 |
| --- | --- | --- | --- |
| 配置参数 | `TestConfig` | 测试开始前由用户或系统设定，参与采集、停止、过滤、计算。 | `treadmill_speed`、`min_contact_time`、`automatic_data_filter` |
| 会话输入/元数据 | `SessionInput` / `SessionMetadata` | 测试开始时冻结的受试者或环境信息，不一定是算法阈值。 | `foot_length_cm_snapshot`、`foot_length_source` |
| 结果参数 | `ResultMetric` | 测试后从光栅事件和配置计算出的逐步或逐周期结果。 | `step_length_cm`、`contact_time_s`、`cadence_steps_per_s` |
| 汇总统计 | `MetricSummary` | 对结果参数做 min/max/mean/std/CV、左右脚、不对称性统计。 | `metric_summaries["contact_time_s"].mean` |

`min_foot_length` 是过滤阈值，`foot_length_cm_snapshot` 是受试者本次测试足长快照，两者不能合并。

## 3. 目标范围

### 3.1 第一阶段必须实现

1. 支持两个独立 test type：
   - `Treadmill Gait Test`
   - `Treadmill Running Test`
2. 跑步机配置参数与纵跳配置隔离。
3. 跑步机测试开始前必须具备：
   - `treadmill_speed`
   - `direction`
   - `foot_length_cm_snapshot`
   - `foot_length_source`
4. 结果报告至少包含：
   - 逐步/逐行结果
   - 左右脚拆分
   - `MetricSummary`
   - 起始脚解析结果
   - 行有效性和统计纳入状态
5. 当前纯光栅 MVP 明确不接入 Gyko/IMU，不生成 IMU 派生指标。

### 3.2 第一阶段不纳入

| 能力 | 不纳入原因 |
| --- | --- |
| 跑步机控制器自动读取速度 | 说明书当前语义是人工填写跑步机设定速度；硬件同步另做集成。 |
| Gyko / IMU 指标 | 属于 OptoJump + Gyko 扩展分析，不是纯光栅跑步机核心。 |
| BioFeedback 训练模式 | 与正式检测模式不同，不保存同一类测试结果。 |
| Video / second monitor feedback | 属于反馈 UI，不影响核心测试配置和结果计算。 |
| 节拍器 | 可作为独立辅助配置，不进入第一阶段核心算法。 |
| 大规模数据库拆表 | 先用 JSON 快照保存完整详情，等查询需求稳定后抽表。 |

## 5. 数据模型建议

### 5.1 跑步机配置与类型别名

第一阶段不单独建立 `common_config.py`。跑步机相关枚举和工具函数先放在 `config/treadmill_config.py` 中；等 reaction、tapping 等模式真正复用这些类型时，再抽成公共文件。

建议在 `config/treadmill_config.py` 中定义两个 dataclass，而不是让一个大类靠可选字段表达所有模式：

```python
from __future__ import annotations

from dataclasses import asdict, dataclass
from typing import Any, Literal

TreadmillTestType = Literal["Treadmill Gait Test", "Treadmill Running Test"]
TreadmillStopType = Literal["Software command", "End of Time"]  # 跑步机 stop_type 有效值子集
Direction = Literal["Interface side", "Opposite side"]
StepLengthCalculation = Literal["Tip-to-Tip", "Heel-to-Heel"]
FootSide = Literal["left", "right", "unknown"]
FootLengthSource = Literal["captured", "manual", "unknown"]
StartingFootSource = Literal[
    "auto_first_contact",
    "auto_double_support_front",
    "manual_override",
    "manual_correction",
    "unknown",
]

def _is_mmss(value: str) -> bool:
    """校验 mm:ss 格式。"""
    import re as _re
    return bool(_re.match(r"^\d{1,2}:\d{2}$", value))

def get_test_length_seconds(value: str | None) -> int | None:
    """将 mm:ss 格式转为总秒数，供算法层使用。"""
    if not value:
        return None
    minute_text, second_text = value.split(":", 1)
    return int(minute_text) * 60 + int(second_text)

@dataclass(frozen=True)
class TreadmillBaseConfig:
    stop_type: TreadmillStopType
    test_length: str | None
    treadmill_speed: float
    direction: Direction
    min_contact_time: int = 60
    min_flight_time: int = 0
    max_flight_time: int = 0
    step_length_calculation: StepLengthCalculation = "Tip-to-Tip"
    min_foot_length: float = 10.0
    filter_gaitr_in: int = 0
    filter_gaitr_out: int = 0
    foot_length_cm_snapshot: float | None = None
    foot_length_source: FootLengthSource = "unknown"
    starting_foot_override: FootSide | None = None

    def __post_init__(self) -> None:
        if not 0.1 <= self.treadmill_speed <= 20.0:
            raise ValueError("treadmill_speed must be between 0.1 and 20.0")
        if self.test_length is not None and not _is_mmss(self.test_length):
            raise ValueError("test_length must be a valid mm:ss string")
        if self.stop_type == "End of Time" and self.test_length is None:
            raise ValueError("test_length is required when stop_type is End of Time")
        if self.min_contact_time < 0 or self.min_flight_time < 0 or self.max_flight_time < 0:
            raise ValueError("time filters must be non-negative")
        if self.min_foot_length <= 0:
            raise ValueError("min_foot_length must be positive")

    def to_dict(self) -> dict[str, Any]:
        return {key: value for key, value in asdict(self).items() if value is not None}

@dataclass(frozen=True)
class TreadmillGaitConfig(TreadmillBaseConfig):
    min_step_length: float = 10.0
    automatic_data_filter: int = 0

    @property
    def test_type(self) -> str:
        return "Treadmill Gait Test"

    def __post_init__(self) -> None:
        super().__post_init__()
        if self.min_step_length <= 0:
            raise ValueError("min_step_length must be positive")
        if self.automatic_data_filter not in (0, *range(10, 91)):
            raise ValueError("automatic_data_filter must be 0 or 10-90")

    def to_dict(self) -> dict[str, Any]:
        data = super().to_dict()
        data["test_type"] = self.test_type
        return data

@dataclass(frozen=True)
class TreadmillRunningConfig(TreadmillBaseConfig):
    min_gap_between_feet: float = 10.0

    @property
    def test_type(self) -> str:
        return "Treadmill Running Test"

    def __post_init__(self) -> None:
        super().__post_init__()
        if self.min_gap_between_feet <= 0:
            raise ValueError("min_gap_between_feet must be positive")

    def to_dict(self) -> dict[str, Any]:
        data = super().to_dict()
        data["test_type"] = self.test_type
        return data
```

配置字段名与 `Iron_parameters.json` / UI schema 保持一致，字段名不带单位后缀；单位必须由 Pydantic `Field(description=...)` 或 schema 的 `unit` 明确声明：

| 字段 | 单位 / 格式 | 说明 |
| --- | --- | --- |
| `test_length` | `mm:ss` 字符串 | 说明书范围 `00:01-59:59`；算法层用 `get_test_length_seconds()` 转为秒。 |
| `treadmill_speed` | `km/h` | 跑步机设定速度；算法层用 `treadmill_speed / 3.6` 转为 `m/s`。 |
| `min_contact_time` | `ms` | 配置阈值；和结果 `contact_time_s` 比较时必须除以 `1000`。 |
| `min_flight_time` | `ms` | 配置阈值；和结果 `flight_time_s` 比较时必须除以 `1000`。 |
| `max_flight_time` | `ms` | 配置阈值；和结果 `flight_time_s` 比较时必须除以 `1000`。 |
| `min_foot_length` | `cm` | 算法过滤阈值，不等于受试者足长快照。 |
| `min_step_length` | `cm` | treadmill gait 专用最小步长过滤。 |
| `min_gap_between_feet` | `cm` | treadmill running 专用两脚最小间隙过滤。 |
| `filter_gaitr_in` / `filter_gaitr_out` | LED 数 | GaitR 进出滤波阈值。 |
| `automatic_data_filter` | `%` | treadmill gait 专用自动数据过滤百分比，`0` 表示关闭。 |

`config/test_config.py` 继续保留旧 `TestConfig`，但需要尽早定义多态配置别名，让类型标注暴露所有适配点。

所有公共字段名与 JSON/UI 一致，`config_from_dict()` 无需任何字段名映射或值转换。

```python
from typing import Any, Union

from config.treadmill_config import TreadmillGaitConfig, TreadmillRunningConfig

AnyTestConfig = Union[TestConfig, TreadmillGaitConfig, TreadmillRunningConfig]

def config_from_dict(data: dict[str, Any]) -> AnyTestConfig:
    test_type = data.get("test_type", "Jump Test")
    payload = {key: value for key, value in data.items() if key != "test_type"}

    if test_type == "Treadmill Gait Test":
        return TreadmillGaitConfig(**payload)
    if test_type == "Treadmill Running Test":
        return TreadmillRunningConfig(**payload)
    return TestConfig.from_dict(data)
```

### 5.2 结果和汇总

第一阶段不单独建立 `report_metrics.py`。`MetricSummary` 和 `summarize()` 先放在 `config/treadmill_report.py` 中；当多个模式复用同一统计层时，再抽成公共模块。

建议在 `config/treadmill_report.py` 中定义：

from dataclasses import dataclass
import math
from typing import Literal

@dataclass(frozen=True)
class MetricSummary:
    count: int
    mean: float | None
    min: float | None
    max: float | None
    std: float | None
    cv_percent: float | None

def summarize(values: tuple[float, ...]) -> MetricSummary:
    if not values:
        return MetricSummary(0, None, None, None, None, None)
    mean = sum(values) / len(values)
    std = math.sqrt(sum((value - mean) ** 2 for value in values) / len(values))
    cv = std / mean * 100 if mean else None
    return MetricSummary(
        count=len(values),
        mean=mean,
        min=min(values),
        max=max(values),
        std=std,
        cv_percent=cv,
    )

Phase 1 不把 `acceleration_m_s2` 放入通用逐步结果：恒定带速下它通常没有信息量。Run Data 中的 `Height` 可在后续 running-only 阶段作为 `flight_time_derived_height_cm` 单独评估，但不能放进 gait/running 共用字段，也不能解释为真实重心轨迹。

结果字段使用单位后缀，和配置字段区分开：

| 结果字段后缀 | 单位 |
| --- | --- |
| `_s` | 秒 |
| `_cm` | 厘米 |
| `_m_s` | 米/秒 |
| `_steps_per_s` | 步/秒 |
| `_percent` | 百分比 |

说明书中带 `[s | %]` 的相位指标，Phase 1 先只保存秒值字段，例如 `stance_phase_s`、`swing_phase_s`。后续需要百分比报告时，再增加成对字段，例如 `stance_phase_percent`、`swing_phase_percent`；不要把秒值和百分比混在同一字段中。

## 6. 算法策略

### 6.1 跑步机模式不是普通步态复用

普通地面步态中，受试者相对光栅向前移动；跑步机中，受试者总体位置接近固定，带速由操作者输入。跑步机算法要显式使用：

| 输入 | 用途 |
| --- | --- |
| `treadmill_speed` | 跑步机模式中距离和速度尺度的唯一输入，并作为报告配置快照保存。 |
| `direction` | 对应说明书 `Direction`。表示受试者跑步/行走方向相对接口鼓的位置：接口鼓在跑步机末端时选 `Opposite side`；反之选 `Interface side`。它同时用于判断双支撑起始时哪只脚在跑步机前方。 |
| `foot_length_cm_snapshot` | 参与足部簇长度判断、脚尖/脚跟参考点计算、历史结果复算。 |
| `step_length_calculation` | 决定 `step_length_cm` 使用 toe-to-toe 还是 heel-to-heel。 |
| `min_step_length` | gait 专用，过滤不合理步长。 |
| `min_gap_between_feet` | running 专用，过滤两脚最小间隙。 |
| `automatic_data_filter` | gait 专用，控制统计纳入状态。 |

跑步机模式中，LED 位置数据主要用于触地/腾空时序、toe/heel 方向、足长过滤、左右脚和起始脚判定；不要把普通地面步态的空间位移公式直接套到跑步机上。距离和速度指标按带速和时间间隔反算：

```text
speed_m_s = treadmill_speed / 3.6
total_distance_cm = speed_m_s * elapsed_time_s * 100
step_length_cm = speed_m_s * step_time_s * 100
stride_length_cm = speed_m_s * gait_cycle_s * 100
```

若 running 行中当前步间隔由 `contact_time_s + flight_time_s` 表示，可用该值与 `step_time_s` 对齐校验；不要把 `contact_time_s + flight_time_s` 泛化为所有 gait/running 场景的步长公式。

时间字段有两套单位：配置阈值使用毫秒，结果明细使用秒。所有阈值比较必须显式换算：

```text
min_contact_time_s = min_contact_time / 1000
min_flight_time_s = min_flight_time / 1000
max_flight_time_s = max_flight_time / 1000
```

### 6.2 建议处理流水线

```text
raw 96-bit frame
  -> extract_clusters(bits)
  -> foot candidate classification using foot length and interface-relative direction
  -> contact/lift event stream
  -> resolve starting foot
  -> accumulate step rows
  -> apply threshold filters
  -> apply gait automatic data filter
  -> summarize included rows
  -> build TreadmillGaitReport / TreadmillRunningReport
```

### 6.3 起始脚策略

1. 若 `starting_foot_override` 是 `left` 或 `right`，测试开始时先采用人工覆盖，并设置 `starting_foot_source = "manual_override"`。
2. 若没有人工覆盖，START 后第一只触地脚为起始脚，设置 `starting_foot_source = "auto_first_contact"`。
3. 若 START 时处于双支撑，使用 `direction` 判断跑步机前方脚，设置 `starting_foot_source = "auto_double_support_front"`。
4. 测试后人工修正时，更新 `resolved_starting_foot` 和 `starting_foot_source = "manual_correction"`，但保留原始 row 数据。

### 6.4 有效性策略

每一行结果都要同时保存事件有效性和统计纳入状态：

| 字段 | 作用 |
| --- | --- |
| `is_event_valid` | 表示原始事件是否通过接触/腾空/步长/足长阈值。 |
| `is_included_in_statistics` | 表示该行是否参与均值、标准差、CV、左右脚统计。 |
| `event_invalid_reason` | 解释事件为什么无效。 |
| `statistics_exclusion_reason` | 解释事件有效但为什么不参与统计。 |
| `correction_source` | 对齐阈值过滤、自动过滤、手动删除/恢复等来源。 |

### 6.5 Suspended 策略

`RowStatus` 中保留 `suspended`，但 Phase 1 不生成 suspended 行。当前阶段的暂停/恢复策略是：

1. 暂停期间 processor 不累计 step row，也不纳入统计。
2. 恢复后不重新判定 `resolved_starting_foot`，避免同一次测试出现多个起始脚。
3. `suspension_segments` 可以先保存为空元组；后续实现暂停段时再记录开始/结束时间。
4. 需要支持说明书级别的 `Suspended` 行时，再把暂停段转换为 `row_status = "suspended"` 的报告行。

## 11. 最小可交付定义

跑步机模式第一版完成时，需要满足：

1. UI 可选择 `Treadmill Gait Test` 和 `Treadmill Running Test`。
2. 参数面板只展示该模式适用的配置参数。
3. 测试开始前保存跑步机速度、跑步/行走方向相对接口鼓的位置、足长快照和足长来源。
4. 跑步机模式不会进入普通步态 processor。
5. 结束后生成 `TreadmillGaitReport` 或 `TreadmillRunningReport`。
6. 报告可展示逐步结果、有效性、统计纳入状态、汇总统计和配置快照。
7. 数据库可保存配置快照、报告摘要、报告详情。
8. 纵跳测试的既有报告和保护测试仍通过。

## 12. 我建议的开工顺序

最稳的顺序是：

1. `TreadmillConfig` 和 `AnyTestConfig` 先落地。
2. `TreadmillReport` 和 `MetricSummary` 先落地。
3. 再改 `GaitEngine` 为 facade。
4. 接 treadmill processor。
5. 最后接 UI、数据库、agent。

原因是配置和报告是边界层，先稳定边界可以减少算法实现中来回改字段名的成本。`SessionController` 暂时不拆，避免把生命周期问题和算法问题绑在一起。
