# IronJump 主 UI 重构：业务行为与交互规格

> 状态：当前业务行为基线；用户/团队、暂停计时与 Report Agent 行为已回写
> 日期：2026-08-10
> 范围：运动员、测试、结果、设置四个应用级模块
> 非目标：不以旧控件和新控件的一对一对应作为验收条件；本轮不全量移除 Dayu，也不实现侧栏折叠

## 1. 目的与原则

本规格用于约束后续 Figma 设计和 PySide6 实施。UI 可以合并、拆分、移动或替换控件，但必须显式处理现有业务行为、已知缺口和新增能力。

核心原则：

1. **保持业务契约，不保持控件形状。** 验收对象是输入、规则、状态、副作用、输出和异常恢复。
2. **不把当前实现缺陷误当成必须保留的业务。** 例如设备连接失败后仍显示“运行中”是缺口，不是目标行为。
3. **不把原型图中的文案当成已经存在的能力。** “设备已连接”“临时结果可重新关联”等必须有后端状态和持久化支持。
4. **新旧流程发生语义变化时单独确认。** 特别是启动时序、暂停计时、匿名结果保存和结果重新关联。
5. **当前只正式暴露已实现的三种测试。** 即 `Jump Test`、`Treadmill Gait Test`、`Treadmill Running Test`。

## 2. 当前系统的权威行为边界

### 2.1 主链路

当前正式主流程是：

```text
选择受试者（可空）
  → 智能配置确认 / 手动配置
  → 创建 SessionSetup 并离开配置编辑状态
  → prepare(config)，创建 USB Worker 与算法引擎
  → 进入执行页
  → 用户点击“开始采集”
  → USB 采集与算法处理
  → 自动结束 / 手动结束
  → 先停止线程，再构造独立报告快照
  → 正式运动员或临时测试均写入 SQLite
  → 显示当前报告
  → 可手动导出 Excel
```

代码依据：

- 配置提交与视图跳转：[ui/main_window.py](../ui/main_window.py#L225)
- 会话资源准备与启动：[ui/session_controller.py](../ui/session_controller.py#L80)
- 停止后构造报告：[ui/session_controller.py](../ui/session_controller.py#L219)
- 关联受试者时自动存档：[ui/main_window.py](../ui/main_window.py#L260)
- 报告导出：[ui/views/report_view.py](../ui/views/report_view.py#L858)

### 2.2 当前会话状态

当前代码仍未引入统一的会话状态枚举，但设备状态已经结构化，会话行为可还原为：

```text
CONFIG_DRAFT
  → CONFIG_CONFIRMED
  → PREPARED
  → RUNNING
  ↔ PROCESSING_PAUSED
  → STOPPING
  → REPORTED
```

仍未完整建模的异常状态：

- 报告构建失败只记录日志，不会发射 `session_finished`。
- 存档失败不阻止当前报告显示，但 UI 不会告知用户“报告未存档”。
- 准备阶段返回配置会明确丢弃未开始的会话；运行中关闭或切换模块会先结束并构造报告。

目标实现必须使用明确状态，而不是从按钮是否显示反推状态：

```text
CONFIG_DRAFT
CONFIG_READY
PREPARING
DEVICE_WAITING
READY_TO_ACQUIRE
RUNNING
PAUSED_PROCESSING
STOPPING
REPORT_READY
SAVE_FAILED
DEVICE_ERROR
REPORT_ERROR
```

## 3. 当前业务行为清单

### 3.1 运动员/受试者

当前已实现：

- 本地 SQLite 保存运动员档案。
- 支持创建、搜索、更新、归档，以及“无历史时删除、有历史时归档”。
- 档案字段包括姓名、性别、出生年份、身高、体重、实测足长、训练水平、训练侧重和备注。
- 支持团队及用户—团队多对多成员关系；同一用户可以加入多个团队，也可以处于“未加入团队”。
- 创建用户时可选择已有团队、新建团队或暂不加入；同名同出生年会提示复用已有档案或继续新建。
- 测试页可以不选择受试者；该路径属于临时测试。
- 选择受试者后，配置助手会读取其档案及最近三次测试摘要。
- 可以从该受试者历史中加载上次配置。
- 正式用户开始测试前必须选择已加入团队或“不以团队身份测试”。

代码依据：

- 本地数据库路径与模型：[data/subject_store.py](../data/subject_store.py#L24)
- CRUD 与归档规则：[data/subject_store.py](../data/subject_store.py#L91)
- 最近历史转换为助手上下文：[data/subject_store.py](../data/subject_store.py#L338)
- 测试页受试者选择：[ui/views/setup_view.py](../ui/views/setup_view.py#L235)

当前限制：

- 测试页编辑的人体与训练信息默认只进入本次会话快照，不自动更新运动员主档案。
- 只有用户显式确认“更新运动员档案”时，安全字段才整体写回；出生年份仍在运动员管理页维护。
- 登录、角色权限、云同步和跨设备身份合并尚未实现。

目标语义：

- “运动员”模块管理主档案。
- “测试”模块只选择测试对象并创建**会话快照**。
- 测试页修改的临时信息默认只影响本次会话；只有用户明确选择“更新运动员档案”时才写回主档案。
- 报告永远保留测试开始时的会话快照，之后修改运动员主档案不能篡改历史报告。
- 每次测试只保存一条 session。正式用户测试始终归属该用户；选择团队时额外保存测试时团队身份和团队名称快照。

### 3.2 智能配置与手动配置

当前已实现：

- 智能配置有在线 LLM 与离线规则两条路径。
- 在线 LLM 支持三种已实现测试，结构化输出转换为对应配置类型。
- 离线规则目前只支持 `Jump Test`。
- LLM 或规则生成的是待确认建议；用户确认后才成为当前配置。
- 运动员信息、测试类型或训练侧重变化会使待确认建议失效。
- 手动配置从参数 schema 动态生成表单。
- 智能配置、手动配置、上次参数、历史参数最终都汇聚为 `AnyTestConfig`。

代码依据：

- 建议配置与显式确认：[ui/views/agent_config_panel.py](../ui/views/agent_config_panel.py#L502)
- 离线规则仅支持纵跳：[ui/views/agent_config_panel.py](../ui/views/agent_config_panel.py#L576)
- 配置来源汇聚：[ui/views/setup_view.py](../ui/views/setup_view.py#L470)
- 动态手动配置：[ui/param_panel.py](../ui/param_panel.py#L101)

目标语义：

- “发送”只请求建议，不直接改变有效测试配置。
- “应用建议配置”是一次显式提交操作。
- 建议生成后，如果运动员会话快照或测试类型发生变化，该建议必须标记为过期。
- 手动配置与智能配置必须经过同一套最终校验，不能只依赖输入控件的范围。
- 切换配置方式时保留当前已确认配置；未确认建议可以丢弃，但必须明确提示。
- “配置来源”作为会话元数据保存：`agent`、`manual`、`last_session` 或 `history`。

### 3.3 参数和算法接口

当前正式运行配置类型：

| 测试 | 配置类型 | 处理器 | 主要输出 |
|---|---|---|---|
| 纵跳 | `TestConfig` | `JumpProcessor` | 触地/腾空、跳高、接触时间、腾空时间、节奏 |
| 跑步机步态 | `TreadmillGaitConfig` | `TreadmillProcessor` | 逐步结果、足迹、步态周期、阶段、左右统计 |
| 跑步机跑步 | `TreadmillRunningConfig` | `TreadmillProcessor` | 逐步结果、腾空/接触、足迹、步态周期、左右统计 |

代码依据：

- 配置分发：[config/test_config.py](../config/test_config.py#L119)
- 引擎分发：[engine/gait_engine.py](../engine/gait_engine.py#L156)
- 纵跳计算：[engine/modes/jump_processor.py](../engine/modes/jump_processor.py#L73)
- 跑步机计算：[engine/modes/treadmill_processor.py](../engine/modes/treadmill_processor.py#L148)

必须保持的算法边界：

- USB 算法输入是 96 位 `contact_bits` 与 `time.perf_counter()` 时间戳。
- README 和硬件设计的标称采样率为 1000Hz，当前 UI 和算法不提供修改；但运行时只接收逐帧时间戳，没有验证设备实际采样率。原型若显示该值，应标为“标称 1000Hz”或同时区分“实测采样率”，不能作为可编辑建议参数，也不能把静态值当作连接诊断。
- 运行算法必须使用测试开始前确定的配置快照。跑步机配置是 frozen dataclass；纵跳 `TestConfig` 当前仍可变，只是进入执行页后不再提供编辑入口，目标实现需要显式复制或冻结。
- 报告必须在采集线程停止后构造。
- `ReportView` 消费脱离运行引擎的报告快照，不读取运行中的引擎状态。当前报告类型使用 frozen dataclass；需要保持的是快照边界，而不是依赖“深度不可变”这一实现细节。
- 视觉模块当前不写回正式算法、报告或历史，不得在新 UI 中表述为已参与正式计算。

配置字段的实际消费关系：

| 字段 | 当前消费者 | 实际行为 |
|---|---|---|
| `test_type` | `GaitEngine` | 选择纵跳、跑步机步态或跑步机跑步处理器 |
| `stop_type`、`number_of_jumps`、`test_length` | `GaitEngine` | 次数自动停止、时间自动停止或手动停止 |
| `min_contact_time`、`min_flight_time`、`max_flight_time` | 各模式 processor/accumulator | 过滤、合并或丢弃过短/过长事件 |
| `treadmill_speed`、`direction` | 跑步机 accumulator | 计算带速位移、距离、速度和方向符号 |
| `step_length_calculation` | 跑步机 accumulator | 选择 Tip-to-Tip 或 Heel-to-Heel 参考口径 |
| `min_step_length` | 跑步机步态 accumulator | 过滤过短步长 |
| `automatic_data_filter` | 跑步机 accumulator | 报告构建前执行自动数据过滤 |
| `min_gap_between_feet` | 跑步机跑步 accumulator | 标记/过滤过小脚间距 |
| `foot_length_cm_snapshot` | `TreadmillProcessor` | 调整脚跟/脚尖偏移并进入报告快照 |
| `foot_length_source` | 报告 | 记录足长来源，不直接改变计算 |
| `starting_foot_override` | 跑步机 processor/accumulator | 覆盖自动起始脚映射 |

当前只有数据字段、没有正式运行消费者的配置包括：

- 纵跳的 `start_type`、`start_position`、`finish_position`、`starting_foot`。
- `metronome_enabled`、`metronome_bpm`。
- 跑步机的 `min_foot_length`、`filter_gaitr_in`、`filter_gaitr_out`。

这些字段不能仅因为出现在 `Iron_parameters.json` 中就被视为已实现功能。

人体参数的真实影响范围：

- 年龄、体重、身高、训练水平和训练侧重当前用于配置助手上下文。
- 当前纵跳高度由腾空时间计算，体重和身高不直接参与该公式。
- 跑步机的 `foot_length_cm_snapshot` 会影响脚跟/脚尖偏移和步长计算。
- 因此临时档案提示应写成“默认档案会影响推荐配置；足长快照会影响跑步机相关计算”，不能笼统声称所有人体参数都会改变算法结果。

### 3.4 设备接口

当前行为：

- `prepare(config)` 创建 `QThread`、`UsbWorker` 和 `GaitEngine`，并只打开设备进行预检，不启动正式采集。
- `UsbWorker` 通过 `DISCONNECTED / CONNECTING / CONNECTED / STREAMING / ERROR` 结构化状态报告设备生命周期。
- 只有设备为 `CONNECTED` 且用户点击“开始采集”后，Controller 才请求采集；收到 `STREAMING` 后才把会话标为运行中并启动算法计时。
- 连接失败停留在可重试状态，也可以返回配置；不会生成测试报告或进入 `RUNNING`。

代码依据：

- 资源准备：[ui/session_controller.py](../ui/session_controller.py#L80)
- 启动时序：[ui/session_controller.py](../ui/session_controller.py#L129)
- USB 成功和失败消息：[hardware/usb_worker.py](../hardware/usb_worker.py#L243)

目标契约：

```text
DeviceState =
  DISCONNECTED
  | CONNECTING
  | CONNECTED
  | STREAMING
  | ERROR
```

- `UsbWorker` 或设备适配层必须发射结构化状态和错误原因。
- 进入测试界面后先执行设备打开和预检，状态依次进入 `PREPARING`、`READY_TO_ACQUIRE`；这个阶段不得自动开始正式采集。只有用户在测试界面明确点击“开始采集”后才能进入 `RUNNING`。如果底层设备必须提前持续读帧才能确认就绪，点击前的帧也必须丢弃，不进入计时、算法结果或报告。
- USB 打开失败不得进入 `RUNNING`。
- 设备状态区可以成为“设置/诊断”入口，但状态本身不能依赖解析 UI 文本。
- “设备已连接”不能在配置页静态写死。

### 3.5 运行、暂停和结束

当前行为：

- 配置页“开始测试”实际上只准备资源并进入执行页。
- 执行页“开始采集”才启动设备和算法。
- 暂停只让引擎丢弃后续帧，USB 仍继续采集。
- 暂停期间 UI 倒计时、引擎 `End of Time` 自动结束计时器和数据时间轴同时冻结；恢复后从剩余时间继续。
- 纵跳可按目标次数自动结束；所有支持时长的测试可按时间自动结束；也可手动结束。
- 自动结束信号延迟 200ms 后停止，以便处理最后事件。

代码依据：

- 两阶段启动：[ui/main_window.py](../ui/main_window.py#L225) 与 [ui/views/execution_view.py](../ui/views/execution_view.py#L799)
- 暂停生命周期与计时协调：[ui/session_controller.py](../ui/session_controller.py) 与 [ui/views/execution_view.py](../ui/views/execution_view.py)
- 自动结束：[engine/gait_engine.py](../engine/gait_engine.py#L480)

首版重构必须保持以下业务条件：

1. 采集前已有通过统一校验、不可在运行中漂移的配置快照。
2. 参数配置完成后只进入测试准备界面，不自动开始采集。
3. 用户必须在测试界面再次点击“开始采集”，明确授权本次正式采集。
4. 设备打开失败时停留在可恢复状态，不能把会话记为 `RUNNING`。

两阶段启动已经确认：配置页主操作为“进入测试准备”，进入测试界面后进行设备准备、站位或相机预览；设备就绪后仍必须由用户点击“开始采集”。静态原型中的单个“开始测试”不能同时承担配置提交和正式采集，也不能在进入测试界面后自动触发采集。

暂停语义已经统一为“暂停会话且冻结计时”。USB 可以继续保持连接，但暂停期间帧不进入正式算法统计，倒计时和自动结束不会消耗剩余时长，恢复后数据时间线从暂停点继续。任何后续改动都必须同时覆盖引擎计时器、UI 倒计时、事件时间线和报告口径，不能只改按钮文案。

### 3.6 报告、历史和导出

当前已实现：

- 测试停止后生成脱离运行引擎的报告快照并立即显示。
- 正式运动员和临时测试都会保存配置、会话人体参数快照、报告摘要和完整报告详情。
- 数据库允许 `subject_id` 为空，旧的非空 schema 会自动迁移且保留原记录。
- 结果页可全局列出本地测试、按运动员查看、加载历史参数、重新打开历史报告，并把临时结果事后关联到正式运动员。
- 个人历史按 `subject_id` 查询该用户全部测试；团队历史按测试时 `team_id` 查询代表该团队完成的测试。两者引用同一条 session，不复制报告。
- 主流程保存真实采集开始与结束的墙钟时间。
- 报告页可以导出 Excel。
- 报告页已提供唯一的“智能分析”入口。用户点击后才启动 Report Agent；正式报告先行生成，Agent 失败不会影响正式报告。
- 智能分析结果来自受限 AnalysisPlan、确定性 Kernel 和 Claim Validator；用户不能用它改写正式测量值。

当前限制：

- 跑步机详情保存 canonical 足迹时间线，但不复制体积较大的原始 USB 帧。
- Excel 导出后没有把生成路径回写 `export_path`。

代码依据：

- 当前数据库结构与报告重建：[data/subject_store.py](../data/subject_store.py)
- 会话存档：[ui/main_window.py](../ui/main_window.py)
- 全局结果与报告重开：[ui/views/history_view.py](../ui/views/history_view.py)

## 4. 匿名/临时测试的确定语义

“临时测试人员”不是一个伪造的正式运动员。目标模型是**可持久化但暂未关联运动员的测试会话**。

### 4.1 会话身份

```text
subject_mode = "registered" | "temporary"
subject_id = 正式运动员 ID | NULL
subject_snapshot = 测试开始时冻结的人体与训练信息
```

临时测试的默认会话快照：

- 年龄：30
- 体重：70kg
- 身高：170cm
- 训练水平：`intermediate`
- 训练侧重：均衡
- 足长：未知，跑步机测试时需要单独确认或采集

这些值是可编辑的“通用参数预设”，不是数据库中的公共运动员。

### 4.2 保存与统计

- 临时测试必须和正式测试一样保存配置快照、报告快照、结束原因和时间。
- `subject_id` 允许为空。
- 临时测试出现在“结果”列表，并清楚标记“未关联”。
- 未关联时不进入任何正式运动员趋势统计。
- 临时测试可以在结果详情中关联到现有运动员。
- 关联后可以进入该运动员趋势，但历史会话快照保持不变。
- 重新关联只改变归属关系，不用当前运动员档案覆盖测试时快照。
- 若需解除或改绑，属于数据修订操作，应有确认提示；首版不要求审计日志。

### 4.3 已接入的持久化变化

首轮实现已经完成：

- `test_sessions.subject_id` 改为可空，并包含旧 schema 数据迁移。
- 增加 `subject_mode` 或用 `subject_id IS NULL` 明确推导临时状态。
- 增加统一的 `subject_snapshot_json`。
- 为三种正式测试保存可重建的版本化 `report_detail_json`。
- 真实记录采集开始、结束时间；不能用报告保存时间同时代替两者。
- 报告重建不依赖仍存活的内存对象；大体量原始 USB 帧不写入 SQLite。
- 增加 `link_session_to_subject(session_id, subject_id)`。
- 全局结果查询不能要求先传 `subject_id`。

## 5. 四个应用级模块的行为归属

### 5.1 运动员

负责：

- 搜索、创建、查看、编辑、归档运动员。
- 创建、重命名、归档团队并管理用户的多团队成员关系。
- 展示运动员基本档案和已关联测试摘要。
- 按团队筛选用户，并展示当前所属团队。
- 从运动员详情发起测试，并将该运动员带入测试会话。

不负责：

- 控制 USB 设备。
- 编辑某次历史报告的会话快照。
- 承载完整报告分析工作区。

### 5.2 测试

内部包含四个子阶段，侧栏始终保持“测试”选中：

1. `CONFIGURE`：选择正式运动员或临时测试，生成/编辑配置。
2. `PREPARE`：冻结配置与会话快照，创建运行资源，检查设备。
3. `ACQUIRE`：实时采集、暂停会话并冻结计时、恢复、手动结束和自动结束。
4. `FINALIZE`：停止线程、构造报告、保存会话。

配置原型各区域的真实用途：

| 原型区域 | 业务用途 | 必要状态 |
|---|---|---|
| 测试对象 | 选择正式运动员或临时模式，形成会话快照 | registered / temporary |
| 年龄、体重、身高 | 助手上下文和会话快照，不默认写回主档案 | clean / edited |
| 智能配置 / 手动配置 | 选择配置产生方式 | agent / manual |
| 配置助手 | 请求建议或澄清，不直接提交配置 | unavailable / ready / generating / clarification / error |
| 建议配置 | 显示待提交配置及来源 | empty / pending / stale / applied |
| 应用建议配置 | 将建议提交为当前有效配置 | enabled / disabled |
| 设备状态 | 真实设备连接与采集状态 | disconnected / connecting / connected / streaming / error |
| 配置页底部主操作 | 提交配置并进入测试准备界面，不开始采集 | disabled / enabled / preparing |
| 测试界面主操作 | 用户明确点击“开始采集”后才进入正式采集 | disabled / ready / starting |

### 5.3 结果

负责：

- 全局列出正式和临时测试。
- 按运动员、测试类型、日期和关联状态过滤。
- 按团队查看测试时代表该团队完成的记录。
- 打开完整、只读的历史报告。
- 导出报告或原始数据。
- 将临时测试关联到运动员。
- 从历史测试复制配置，跳转到“测试”模块。
- 对当前或历史报告发起只读智能分析，并显示已持久化的分析结果。

不负责：

- 修改历史算法结果。
- 用当前配置重新计算并覆盖原报告。
- 直接编辑运动员主档案。

### 5.4 设置

当前没有独立的持久化设置服务，因此首版设置模块应控制范围：

第一阶段可以提供的内容：

- 设备连接状态、VID/PID、DLL 路径和连接诊断的只读展示。
- 本地数据库路径和导出目录的只读展示。
- LLM Worker 状态及“在线 LLM / 离线规则”的能力说明。
- 相机可用性和当前默认相机的只读展示。

后续确认持久化和生效时机后再增加编辑：

- USB 超时、读取块大小和 UI 刷新率。
- 默认相机与相机默认参数。
- 临时测试通用档案预设。
- 默认导出路径。

未经确认前，不把环境变量编辑器直接做进设置页。设置页也不包含账号、登录、角色权限或云同步。

## 6. 保留、重组、新增和暂不暴露

### 6.1 保留

- 三种已实现测试及其配置模型、算法分发和报告类型。
- 智能建议与显式应用之间的确认边界。
- 在线 LLM、纵跳离线规则和手动配置三种能力。
- 配置在采集前冻结。
- 执行页的实时指标、足迹、相机、周期和进度。
- 暂停分析、手动结束和自动结束。
- 本地 SQLite、历史参数复用和 Excel 导出。
- 报告快照与运行中引擎隔离。
- `ui/data_show.py` 作为回退入口。

### 6.2 重组

- 运动员完整管理从测试页移到“运动员”，测试页保留选择和轻量入口。
- 受试者历史从测试页菜单移到“结果”，同时保留“复用该次参数”。
- Setup、Execution、Report 继续作为测试业务阶段，但由应用级导航承载。
- 多个相机入口可以重组为一个相机区域和设置菜单，只要三种现有相机能力不被静默删除。
- 配置摘要可从底部文字条重组为右侧结构化摘要。

### 6.3 新增

- 应用级固定展开侧栏。
- 明确的会话状态和设备状态。
- 设备就绪门控与可解释的禁用原因。
- 临时测试持久化、全局结果列表和事后关联。
- 统一、版本化的完整报告快照和历史报告重开。
- 会话级人体/训练信息快照。
- 活跃测试期间的导航保护。
- 手动配置、历史配置和智能配置的统一最终校验。
- 最小设置/诊断模块。

### 6.4 暂不在新主流程暴露

以下项目存在字段或旧 UI，但没有完整运行时行为，不能在新 UI 中伪装为可用能力：

- `Reaction Times`、`Sprint and Gait Test`、`Tapping Test`、`Static Test (Sway)`。
- `External impulse` 已确认不属于当前硬件能力，并已从产品配置中移除。
- `start_position` / `finish_position` 的自动检测与门控。
- 节拍器播放；当前只有配置字段，没有主流程运行实现。
- 跑步机 `min_foot_length`、`filter_gaitr_in`、`filter_gaitr_out` 的运行时过滤；当前只有模型和表单字段。
- 视觉脚别结果写回正式算法或报告。
- 可编辑“采样率”；当前产品约定的是标称 1000Hz，运行时尚未验证实测值。
- 登录、云同步和多角色权限。

为兼容旧配置，这些字段可以继续被数据模型读取，但不应作为新主流程的可用功能展示。

## 7. 原型与当前业务的不一致

### P0：实施前必须解决

1. **原型只有一个“开始测试”，当前代码把配置确认、资源准备和开始采集拆成不同阶段。**
   - 已解决：配置页进入测试界面后不能自动采集，设备就绪后必须再次点击“开始采集”。
2. **原型显示设备已连接，当前没有结构化设备状态。**
   - 已解决：设备层发射结构化状态，配置页不静态声称已连接。
3. **原型承诺临时结果可关联，当前匿名测试不保存。**
   - 已解决：匿名测试保存可空归属和会话快照，并支持事后关联。
4. **原型有“结果”模块，当前历史无法重新打开完整报告。**
   - 已解决：结果模块可从持久化详情重建并打开报告。
5. **当前手动配置没有统一调用 `ParamSchema.validate()`。**
   - 已解决：智能、手动、上次和历史配置进入同一最终校验入口。
6. **手动配置会显示未实现测试类型。**
   - 已解决：新 UI 只显示三种正式模式，并隐藏节拍器和 External impulse。

### P1：需要随对应模块处理

1. 测试页临时修改的运动员信息已写入会话快照，但“更新运动员主档案”仍需显式入口。
2. 暂停冻结 UI 倒计时、自动结束计时器和数据时间轴；恢复后从剩余时间继续。
3. USB 打开失败已停留在设备错误状态，不会进入运行中。
4. 报告构建失败或存档失败缺少用户可见恢复。
5. Excel 导出路径没有回写会话记录。
6. 当前会话已保存真实采集开始和报告完成的墙钟时间。
7. 设置页没有持久化模型，现有硬件配置来自环境变量。
8. 运行中导航已提供留在测试、结束保存和结束标记异常三种选择。

## 8. 可验证的交互场景

### S1 正式运动员 + 智能配置 + 自动结束

1. 选择正式运动员。
2. 系统创建会话快照并加载最近历史给配置助手。
3. LLM 生成建议；当前有效配置仍未改变。
4. 用户应用建议，统一校验通过。
5. “进入测试准备”启用。
6. 设备连接成功，执行页进入 `READY_TO_ACQUIRE`。
7. 用户点击“开始采集”，状态进入 `RUNNING`。
8. 达到目标次数或时间后自动停止。
9. 线程停止后生成报告并保存。
10. 当前报告显示，且“结果”列表可以重新打开同一报告。

验收：配置快照、会话快照、报告快照、结束原因和运动员归属一致。

### S2 临时测试 + 事后关联

1. 选择“临时测试”，载入通用档案预设。
2. 用户修改会话参数但不创建正式运动员。
3. 完成测试后保存为 `subject_id = NULL`。
4. 结果列表显示“未关联”，不进入任何运动员趋势。
5. 用户在结果详情关联已有运动员。
6. 该结果进入对应运动员历史，原会话快照不变。

验收：关联前后报告内容和测试时人体快照完全一致，只改变归属。

### S3 手动配置校验

1. 切换到手动配置。
2. 选择三种正式模式之一。
3. 修改停止方式后，仅要求当前方式需要的字段。
4. 所有字段经过统一 schema 和跨字段校验。
5. 无效配置不能进入准备阶段，并显示具体错误。

验收：手动配置、智能配置和历史配置使用同一最终校验结果。

### S4 智能服务不可用

1. LLM Worker 初始化失败或断开。
2. UI 显示真实错误，不显示“LLM 已连接”。
3. 纵跳仍可使用离线规则。
4. 三种模式均可转用手动配置。

验收：智能服务故障不阻断本地核心测试流程。

### S5 设备连接失败

1. 配置已确认，进入测试准备。
2. USB 打开失败。
3. 状态进入 `DEVICE_ERROR`，不能进入 `RUNNING`。
4. UI 显示失败原因，并允许重试或返回配置。

验收：无设备数据时不会生成一份看似正常的空报告。

### S6 暂停与时间测试

1. 启动 `End of Time` 测试。
2. 点击“暂停”。
3. USB 保持连接，但正式算法不纳入暂停期间帧；UI 倒计时、自动结束计时器和数据时间轴冻结。
4. 等待一段时间后恢复，剩余时间不因暂停而减少。
5. 恢复后从剩余时间继续，并在有效采集时长耗尽时自动结束。

验收：暂停前后 UI 剩余时间、引擎自动结束和报告有效时长口径一致，不存在暂停期间自动结束或时间轴跳跃。

### S7 运行中导航

1. 测试处于 `RUNNING` 或 `PAUSED_PROCESSING`。
2. 用户点击运动员、结果或设置。
3. 系统不直接销毁执行页。
4. 弹出明确选择：留在测试、结束并保存、结束且标记异常。

验收：不存在静默中止、后台继续采集或报告丢失。

### S8 报告或存档失败

1. 采集结束后报告构建失败，进入 `REPORT_ERROR` 并保留诊断信息。
2. 报告成功但 SQLite 写入失败，显示当前报告并进入 `SAVE_FAILED`。
3. 用户可以重试保存或导出当前报告。

验收：不能只写日志而让用户误以为已经存档。

### S9 历史配置复用

1. 从结果详情选择“使用该次参数再次测试”。
2. 跳转到测试配置，来源标记为 `history`。
3. 当前运动员归属不由历史配置偷偷覆盖。
4. 配置按当前 schema 重新校验后才能进入准备。

验收：复用的是配置，不是旧报告、旧运行状态或隐式运动员身份。

### S10 未实现能力不可误用

验收：

- 新 UI 中没有四种未实现测试。
- 没有可编辑的 1000Hz 采样率。
- 没有可开启但实际不播放的节拍器。
- 没有声称可用的 External impulse。
- 没有声称视觉已经参与正式报告。

## 9. UI 和 Figma 的实施范围

当前单张测试页原型可以保留为视觉方向，但不足以直接指导实现。Figma 下一轮至少需要表达这些状态：

- 正式运动员 / 临时测试。
- 无建议 / 生成中 / 待应用 / 已应用 / 已过期。
- LLM 初始化 / 就绪 / 错误 / 离线规则。
- 配置无效 / 有效。
- 设备未连接 / 连接中 / 已连接 / 错误。
- 准备中 / 可采集 / 运行中 / 暂停分析 / 停止中；按钮数量由最终启动方案决定。
- 报告已保存 / 保存失败。

不要求为每个状态复制完整高保真页面；可以用组件变体、状态表和关键流程帧表达。

首轮 PySide6 实施边界：

1. 先定义会话状态、设备状态和统一配置校验接口。
2. 建立应用级外壳和导航，但不允许运行中无保护切页。
3. 在保持现有算法与报告接口的前提下重组测试配置和执行流程。
4. 完成临时会话持久化和统一报告快照后，再启用“结果”完整能力。
5. 运动员模块复用现有 `SubjectStore`，补全独立编辑流程和会话快照。
6. 设置模块首版以诊断和只读信息为主。
7. 新外壳不新增 Dayu 依赖；旧 View 和回退界面分阶段迁移。

## 10. 实施门槛

在开始大规模 UI 重构前，必须满足：

- [x] 按已确认契约实现并验证两阶段启动：配置提交只进入测试准备界面，设备就绪后必须再次点击“开始采集”，且失败时可重试或返回配置。
- [x] 设备层能提供结构化状态。
- [x] 三种配置来源使用统一最终校验。
- [x] 临时测试的数据库迁移和报告快照格式有自动化测试。
- [x] 历史报告可从持久化快照重建。
- [x] 活跃会话导航规则已实现。
- [x] 当前三种模式的核心回归测试通过。

这组门槛用于防止“新界面完成但核心流程退化”。视觉完成度不替代业务验收。
